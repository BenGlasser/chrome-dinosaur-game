<objective>
Wire the duck mechanic — DINO-03 (visual duck cycle) and DINO-04 (shrunk hitbox while ducking).

This plan is small because the heavy lifting was front-loaded into 02-01:
- 02-01 already shipped the `isDuckHeld` global, the `keyUp(e)` handler, the keyup listener registration, the duck-state branches in the state-derivation block (D-06), the duck-state branches in the hitbox-dims block (D-15), the gravity-skip-while-ducking gate (D-17), and the duck-state branches of the sprite picker (D-04).
- All that's left is to fill in `moveDino`'s currently-empty `else if (e.code == "ArrowDown" && dino.y == dinoY)` branch with `isDuckHeld = true;` AND drop the `&& dino.y == dinoY` ground gate per D-18 (so a player who holds ArrowDown while airborne gets a pre-buffered duck the moment they land).

After this two-line edit, the entire data flow lights up:
- ArrowDown keydown → moveDino sets `isDuckHeld = true`.
- Next `update()` frame: `frameCount++`; state-derivation sees `dino.y == dinoY` (on ground) and `isDuckHeld == true` → `dinoState = "ducking"`. (If still airborne, derivation routes to "jumping" first per D-20 priority — the held flag is harmless.)
- Hitbox-dims block: `dino.width = 118; dino.height = 60; dino.y = 190;`.
- Gravity gate: `velocityY = 0;` (skipped — prevents teleport).
- Sprite picker: `(Math.floor(frameCount / 6) % 2 == 0) ? dinoDuck1Img : dinoDuck2Img` — duck cycle at the same 6-frame interval as the run cycle, satisfying DINO-03's "same rate as the run cycle" clause.
- Drawn at `dino.y = 190`, the dino's feet remain at y = 250 (`190 + 60 = 250`, matching standing `156 + 94 = 250`).
- ArrowDown keyup → `keyUp` clears `isDuckHeld = false` → next frame derives "running" → hitbox restores to standing → gravity resumes.

**DINO-04 hitbox math (canonical, verified — RESEARCH §"Duck Hitbox Math"):**

```
boardHeight = 250

Standing dino:    y=156, height=94 → AABB y-span [156, 250], width 88
Ducking dino:     y=190, height=60 → AABB y-span [190, 250], width 118
                                     ↑ shorter (60 < 94) and wider (118 > 88)

A hypothetical bird at y=150, height=40 → AABB y-span [150, 190]:
  Standing AABB:  y=156 < 190 (TRUE) AND y=250 > 150 (TRUE) → COLLISION
  Ducking AABB:   y=190 < 190 (FALSE — not strictly less)   → NO COLLISION
  Result: standing dino dies; ducking dino passes safely under. CORRECT.
```

This satisfies the ROADMAP success criterion #4 ("a test obstacle at low height does not collide with the ducking dino but does collide with the standing dino") **by calculation**. Empirical confirmation requires a real low obstacle, which doesn't exist in v1.0 until Phase 3's birds (BIRD-03). Per RESEARCH §"Open Questions" Q1 option (c), this is the chosen verification approach for Phase 2 — it is lossless because the hitbox IS correctly sized; Phase 3 closes the empirical loop. **No debug obstacle is added to this plan.**

**Critical traps surfaced by RESEARCH that this plan handles via reliance on 02-01:**

- **Gravity-while-ducking teleport (RESEARCH §Risk 1).** `dino.y = Math.min(dino.y + velocityY, dinoY)` uses `dinoY=156` as the gravity floor. While ducking, `dino.y=190`. Running this clamp would snap the dino UP to 156 (since 190+v > 156). 02-01's gravity gate (`if (dinoState != "ducking") { ... } else { velocityY = 0; }`) prevents this. This plan does not need to re-add the gate; it just relies on it. The acceptance criteria below grep-verify the gate is still present.
- **Stand-up launch artifact (RESEARCH §Risk 4).** If `velocityY` were not zeroed during duck, gravity (`+= 0.4` per frame) would accumulate. On stand-up, that accumulated velocity would apply on the first non-duck frame. 02-01's `velocityY = 0` in the duck branch handles this.
- **Pre-buffered duck on landing (RESEARCH §Risk 3 / D-20).** Player presses ArrowDown mid-jump. State-derivation prioritizes airborne over duck, so `dinoState = "jumping"` while airborne (correct — no in-air duck pose). On landing, derivation flips to "ducking" because `isDuckHeld` is still true. This is desirable feel and is achieved purely by D-18's "drop the ground gate" — which IS the change this plan makes.
- **resetGame() restoring standing hitbox after a duck-state death (RESEARCH §Touchpoint 7 / D-19).** Already shipped in 02-01 Task 3. This plan relies on it; the verification block here re-greps `dino.width = dinoWidth` in resetGame as a regression check.
